Test Run Guide

Each team member creates two fake schools and takes each one all the way from Get a Sample to Ready to Teach. An observer watches over screen share. At every step you check that the automation did its job. Your check-offs save here, so the whole team can see progress.

Dev only.All of this happens on the development portal. Nothing goes to Salesforce, the LMS, or a real school. Payments use Stripe's test card, so no money moves.

How it works

One fake school goes through eight stages. Every stage has things you do and things you check.

Get a sampleWebsite form, as a school
Request a quoteGrades and student counts
OrderAccept the quote
PayStripe test card
Log inWelcome email, set password
OnboardAdmins, contacts, school settings
RosterImport students, then edit
Ready to teachTeachers see their classes

Two kinds of steps

  • Do steps are actions you take. Mark them Done.
  • Check steps are things the system should do on its own: send an email, create a record, change a status. Mark each one Worked, Problem, or Didn't see it.
  • Anything other than Worked needs a short note saying what you saw.

Why the checks matter

Once we go live, schools will order and set up with no one from Deep Roots stepping in. The checks prove that each handoff happens automatically. If you had to nudge something, ask a teammate, or refresh a page to make it happen, record it as a Problem.

Before you start

About 10 minutes, once. After that, each run takes 45–60 minutes.

1. Your test email addresses

You don't need a second email account. Add +something to your work address and the mail still lands in your own inbox. Each fake person gets their own address this way: the buyer, a second admin, teachers.

Enter your email to see your test addresses.

Before your first run, send one email to your +r01 address. Make sure it arrives.

2. Browser and call

  1. Open a private / incognito window for the test, so you aren't signed in as your real Deep Roots self.
  2. Join the video call with your observer and share your whole screen, not one tab. That way they can see emails arrive.
  3. Keep your inbox open in a second tab.
  4. Download your roster file from Roster files.

3. Stripe test cards

Card is declined4000 0000 0000 0002

Use any future expiry date (12/34), any 3-digit CVC (123), and any ZIP (12345). These only work while the portal's Stripe account is in test mode. Never type a real card.

4. Name everything TEST

Use the school name from your scenario exactly as written, including (TEST). This makes test schools easy to find and delete later. Use a made-up street address. Never use a real school's name.

Checklist

Roster files

Each run comes with a ready-made roster: fake student names by grade, plus a teacher for each class. You import it during onboarding, so nobody types students in one at a time. Teacher emails use your + addresses, so their invites come to you. Names are generated the same way every time, so the observer sees the same list you do.

For observers

The tester drives and the observer watches. Your job is to see what a real school would experience.

During the run

  1. Open this page on the same run. You can tick the Check steps while the tester drives.
  2. Ask the tester to think out loud: what they expect, what confuses them.
  3. Don't help unless they've been stuck for 2 minutes. When they get stuck, that's a finding: note it on the step.
  4. Note how long each email takes to arrive. More than 5 minutes is a Problem.
  5. Record the call if you can. It makes bug reports much easier.

What counts as a problem

  • Something that should be automatic needed a person to do it.
  • An email didn't arrive, arrived late, or had wrong or blank details.
  • A number didn't match: student count, price, grades.
  • A change didn't stick after refreshing the page.
  • The tester couldn't tell what to do next.

Suggested rhythm

Run A is observed live, so we learn together and fix the obvious things.

Run B can be done solo with a screen recording once that person's Run A is complete. This keeps calendars lighter, and the recording still shows every step.

Schedule each observed run for 60–75 minutes.

After the run

  1. Every step has a mark, and every Problem has a note.
  2. Log each problem on the portal QA page with the run and step number (for example R05 · 7.4).
  3. Click Mark run complete at the bottom of the checklist.
  4. Leave the test school in place. The dev team will clear test data in one batch.

Open questions for the dev team

Answer these before the first run. Some steps in this guide assume an answer. Where the real button names differ from the ones written here, update the steps.

Which grades does the portal cover?

The scenarios assume K–8 (bands K–5, 6–8 and K–8). If you include pre-K or 9–12, add those grades to the runs.

Do the website's Get a Sample and Request a Quote forms feed the dev portal?

If they go to production, test submissions will create real leads in Salesforce. We need a dev copy of the website or a test flag.

Can a sample request in dev ever trigger a real shipment?

There will be 16 sample requests with fake addresses. Make sure none of them reaches fulfillment.

Is Stripe in test mode on dev?

The 4242 card only works in test mode. Who can open the Stripe test dashboard to confirm that payments landed?

Does dev send real emails, and does it accept "+" addresses?

Half of the checks are "did the email arrive." If dev sends to a catch-all inbox instead, testers need access to it.

What roster format does the import expect?

The files here use: student_id, first_name, last_name, grade, section, teacher_name, teacher_email. Change the columns to match the portal, or add a dev-only "Load sample roster" button.

Where does staff see each automation happen?

For example: a lead list, a quote list, order statuses, an onboarding tracker. Give testers the exact page names so the Check steps can point to them.

How will test schools be cleaned up?

Every test school has (TEST) in its name. Confirm that a batch delete is possible before release.
